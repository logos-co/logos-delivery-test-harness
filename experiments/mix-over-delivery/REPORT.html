Mix over Delivery

What logos-delivery does today, what the open reachability PR stack changes, what issue 183 asks for, and what four hour-long harness runs on a 46-node network measured.

01

Summary

  • Master sends over mix reliably when nothing fails. In an hour of steady traffic it propagated 5,600 of 5,600 Required sends, at a median of 418 ms.
  • Master breaks under churn; the PR stack does not. On a small network, one stopped mix node made a third of master's sends report failure. The stack through #4647 lost nothing when 5 of 25 mix nodes were stopped for 21 minutes.
  • The stack and issue 183 barely overlap. The stack makes today's sends reliable and safe behind NAT. Issue 183's items (cover traffic, Edge/Core wiring, memberships, API cleanup) are untouched by it.
  • Mix over RLN works, but its cost could not be measured at 46 nodes on one host. Proof generation saturated the machine. At 23 nodes it delivered 2,747 of 2,750 sends at a median of 1.6 s, about 1.2 s more than without RLN, using 4.3 cores against about 2 for twice the nodes without it.
  • The measured stack has been withdrawn. Its author replaced it with four mix library PRs and a new delivery train (section 05). The replacement keeps the send-reliability fixes and drops the NAT reply fix; it has not been run in the harness.
02

Current state: master and the PR stack

logos-delivery master 39b5f4ee9

Mix gives sender anonymity on publish and nothing else. Every node that mounts mix is both hop and exit, lightpush is the only exit protocol, and receiving never uses mix.

Works

  • Mount, hop selection (IPv4 TCP/QUIC), static --mixnode list, preset-seeded pool.
  • Mix key advertised through Kad service records and rendezvous.
  • anonymityLevel Preferred / Required: 3-hop path, one single-use reply block, 5 s reply timeout, at least 4 routable pool members.
  • Per-hop Mix RLN (#4282), mix_pool_size gauge, mix in health.

Limits

  • The default anonymityLevel is None; presets list mix nodes but do not enable mix.
  • The mix key is regenerated at every start unless --mixkey is set.
  • No cover traffic. No Edge/Core difference: any mix-mounted node advertises, forwards and exits.
  • discv5 and peer exchange cannot feed the pool (the ENR carries only a capability bit).
  • Preferred falls back to the plain path silently, including for a payload too large for mix (logos-delivery#4690).
  • Uses nim-libp2p-mix at 3f256aa0, 11 commits behind upstream; the missing commits include Sphinx MAC and replay-cache fixes.

Deviations to settle

  • Who advertises. Issue 183 keys it on mode. #4646 keys it on being a service node with a non-observed address. A Core node behind NAT and an Edge node with a public address fall on opposite sides of the two rules.
  • NAT replies. Issue 183 relies on circuit relay to give Edge a reply address. #4631 avoids needing one. They can coexist; if #4631 lands, the issue's dependency on relay limits mostly goes away.
  • Senders are mix nodes too. In every large run the 8 senders also forwarded and exited for others (8 of the 33 exit nodes). Edge mode in issue 183 would stop that; the stack does not.
  • Where the Relay proof is attached. The issue says the exit attaches it. On master the sender does (node/waku_node/lightpush.nim:398), so the issue's Edge rate reasoning does not hold as written.
  • One registry today. The harness ran Relay and Mix on one registry at 10 s, and one membership backed both scopes. It works, and it is the arrangement issue 183 wants to leave.
  • Addressed by none of the three: a Preferred send too large for mix goes out in the clear without notice (logos-delivery#4690).

  • Mix library: four stacked PRs on logos-co/nim-libp2p-mix, #82 → #85 → #86 → #87. The author asks for these to be merged or otherwise resolved first.

What this means for the measurements

  • The runs in section 07 on the #4647 stack show that completing a send on seeing the message again removes master's false errors and the exit-node miss. Fork PR 403 is a different implementation of that idea. Run 5 measured it as part of the fourth train: no false errors, but the exit-node miss is back.
  • With #4729 a private test network needs mix-allow-all-addresses on every node, or the pool stays empty. The harness sets it (MIX_ALLOW_ALL=1, --mix-allow-all-addresses=true).
  • Run 5 (2026-11-16): the fourth train brings the exit-node miss back. manifests/mixnet-23-train4-rln.json is the run 4b network (23 nodes, Mix RLN) on the fourth train tip 27b59e17, built from the fork as image logos-sim:train4-rln (v0.40.0-g27b59e, mix library fe62062, the stack as it was on 2026-11-06, not the current heads). All 2,750 sends were accepted, propagated and confirmed, with no messageError, no reply timeout and one try per message; send → propagated p50 / p90 / p99 was 1,005 / 1,654 / 2,649 ms, faster than run 4b. But no message reached every receiver: each one is missing at exactly one node, the node that was its exit. No node received a message it exited itself, and the per-node miss counts equal the per-node exit counts (121 to 209). This is the fault of master in run 2; it shows on every message here because all 16 exit nodes are module nodes whose receptions are judged. The harness verdict is FAIL for that reason. mix_messages_error_total rose by one per send on each sender (2,750 in total); the cause was not looked into. The module (logos-delivery-module master) does not know the new message_unconfirmed event, so an unconfirmed send would not show in the per-message report; every send here was confirmed.
06

The test harness

A manifest describes groups of nodes; the harness builds one image from pinned sources, generates a Docker Compose stack on a private 10.0.0.0/8 network, runs it for a fixed time and collects events, logs and metrics.

Build

  • One pin: the logos-delivery-module ref. Every other component comes from that module's flake lock.
  • Overrides replace one component: DELIVERY_REF built master, the #4647 stack tip and #4729 for these runs.
  • Nix builds run in a container with a persistent store volume; the result is the image logos-sim:local.
  • RLN is opt-in ("rln": {} in the manifest): the two RLN modules are built too, and three more services run a local LEZ chain.

Node kinds

  • logosdeliverynode: the native node binary, configured by CLI arguments.
  • delivery-module: delivery_module under logoscore, configured by a JSON profile template (conf/*.json.tpl) and environment values.
  • Roles: bootstrap (fixed address and key) and member (count, start delay, jitter).

Traffic and measurement

  • A sender calls the module's send: SEND_COUNT messages every SEND_INTERVAL seconds, with a given ANONYMITY_LEVEL.
  • Every module node records its events (messagePropagated, messageSent, messageError, messageReceived) with a local nanosecond stamp.
  • lib/msg_report.py matches message hashes across nodes: success, latency percentiles, 5-minute steps.
  • Routes: exit node per message and tries per message from node logs; per-node forward counts from Prometheus.
  • Resources: docker stats every 30 s.

Earlier run: a mix pool fed by service discovery

The four cases above hand every sender a static pool. One earlier run, on master 39b5f4ee, did not (manifests/mix-disco-smoke.json): 4 native mix nodes advertising /mix/1.0.0, 2 receivers, and 1 Required sender given no mix nodes, so its pool could fill only through Kad service discovery. It ran for 28 minutes with a send every 20 s.

  • Discovery alone works, after a quarter of an hour. All 49 sends before the pool filled failed with "knows fewer than 4 usable mix nodes". All 31 sends after it succeeded and reached both receivers, at a median of 476 ms.
  • The delay is on the registration side. On mix1, the other mix nodes' /mix/1.0.0 adverts were found exactly 600 s after they started advertising. Their /logos/delivery adverts, registered at the same moment, were found within seconds.
  • Cause: mix is the second service a node advertises, and a registrar penalises it for IP similarity. A registrar makes an advertiser wait according to how many address bits it shares with the adverts it already holds, and the node's own first advert is already there from the same address. The cause is confirmed by a logos-delivery developer; the run itself shows only the timing, since registrars log no wait times. It matches the service-discovery campaign, which measured about 15 minutes of wait per extra service at each registrar (branch experiment/sd-corner-cases, finding 4).
  • What it means for issue 183. With discovery alone, a Required node cannot send for its first quarter of an hour, and a Preferred node sends without mix during that time. The logos.dev and logos.test presets avoid this by seeding mix nodes; a custom cluster has no such seed.
  • Not repeated on the PR stack. #4646 changes who advertises mix, and that was not exercised: every stack run used a static pool.

Limits of this evidence

  • One host. All nodes share 10 cores and one loopback-fast network. There is no added latency, loss or NAT; #4631's NAT behaviour was not exercised.
  • Static pools. Senders were given all mix nodes at start. A discovery-fed pool was tested once, on a small network on master (section 07), where it took about 16 minutes to fill.
  • One run per case. Differences of a few tens of milliseconds are within what a repeat could move.
  • Route data gaps. In runs 2 and 3 one sender's log was cut short at collection, so exit and retry figures cover 7 of 8 senders there. Delivery and latency figures are complete.
  • Stack cells in the matrix are from PR descriptions. Not verified: whether #4646 also stops the ENR Mix bit and the rendezvous record.
  • Not tested: cover traffic, Edge-mode senders, separate Relay and Mix registries, a validating node dropping a message without a proof, rate-limit bursts.
